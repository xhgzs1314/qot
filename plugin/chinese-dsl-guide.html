QOT 扩展开发

语言扩展指南

QOT 的扩展分两个世界：不用碰编译器的扩展（标准库、协议元语、编译期宏） 与必须改编译器的扩展（语言内核本身）。绝大多数需求在前一个世界就能满足， 而且产物与手写代码同价。

1. 先问：真的需要改编译器吗

语言内核是冻结面——它的语法、字节码、原生后端都是稳定契约。扩展之前先在下面三层里找答案：

层 能做什么 写什么
标准库 复用现成能力，封装成模块 .qot 源码（require 引入）
协议元语 让自定义类型参与 +、==、下标、for-in、字符串化 类 + 协议方法
编译期宏 语法级改写：新的关键字、新的语句形态、DSL macro 声明

三层的完整说明见 标准库、协议元语、 编译期宏。只有在这些都做不到时，才需要动编译器。

2. 用宏做中文 DSL

中文关键字不需要改词法器——用宏就能把中文写法映射到既有语法。

// 宏把「如果/那么/否则」映射成 if / else
macro 如果(条件, 那么体, 否则体) {
    return < "kind": "if_statement",
              "condition": 条件,
              "then_body": 那么体,
              "else_body": 否则体 >&;
}

实际使用时把中文体写成语句块，块绑定到形参：

如果(成绩 >= 60) {
    output("及格");
} 否则 {
    output("不及格");
}
为什么用宏而不是改词法器？宏在编译期展开，产物就是普通 if 语句—— 执行性能与手写完全一致；而改词法器会动到语言内核的稳定面，还要同步字节码、原生后端与测试。

3. 用协议做自定义运算

想让自定义类型支持 +、== 或参与 for-in，写协议方法即可， 编译器会在类型可知时把它改写成普通方法直调。

class 时长 {
    var 秒 = 0;
    func init(s) { this->秒 = s; }
    func __add__(其它) { return 时长(this->秒 + 其它->秒); }
    func __to_str() { return int_to_str(this->秒) + "秒"; }
}

output(时长(90) + 时长(30));    // 120秒

完整协议清单与绑定规则见 协议元语。

4. 用宏 + 协议搭一个领域 DSL

把「校验 + 转换 + 报错」这类横切逻辑做成宏，业务代码只写意图：

// 宏：把「字段 = 表达式」改写成「带类型检查的赋值」
macro 字段(目标, 名称, 表达式) {
    return < "kind": "function_call",
              "name": "set_field_checked",
              "args": [目标, 名称, 表达式] >&;
}

配合标准库（校验、统计、文件）与协议（元类型运算），一个小型 DSL 通常只需要几百行 .qot。

5. 扩展语言内核（进阶 · 冻结面）

只有当需求确实无法在库层表达时，才需要改编译器。下面是内核各层的位置与约束——这份地图能帮你判断 「改哪里、要连带改什么」。

层 仓库位置 要连带做的事
词法 token_char.py（关键字表）、grammar.py 的 tokens 新关键字要在词法层登记；__ 前缀是编译器保留
语法 grammar.py（PLY 产生式 + 优先级表） 改产生式必须同步语义分析（visit_*）与节点字段登记表
语义分析 grammar.py 的 visit_* 系列 新节点要有类型推断规则；无法静态判定的事务要明确回落口径
字节码 bytecode.py 新节点要有编译分支；解释器与原生后端两侧都要能跑
中间表示与原生后端 lir_lower.py / lir_opt.py / lir_cgen.py / ot-asset/c/aot/qot_aot_runtime.h 新增指令要同步 LIR 降级、栈模型、优化 pass 与运行时
内置函数 builtins.toml（唯一真相源） 登记后跑三侧对账脚本，确保解释器 / 原生后端 / 清单一致

5.1 改内核的纪律

  1. 先写失败用例：新语法先有一张「应当编译失败」或「应当得到某结果」的钉。
  2. 两侧同改：解释器与原生后端必须同时支持；只改一侧会让差分测试立刻报警。
  3. 清单与文档同步：内置函数改 builtins.toml， 语言能力改 README 与本站手册——文档与实现必须一致。
  4. 三侧对账：内置函数改动后跑一次对账脚本，确认清单与两侧注册面没有漂移。

6. 常见坑

坑 表现 规避
宏不做卫生 宏里的临时变量捕获了调用点的同名变量 宏内临时名统一加 _m_ 前缀
协议绑定依赖类型可知 同一个类在不同调用点绑定了不同的行为 从构造点出发让类型可推断；推断不了就显式调用方法
用了 __ 前缀命名 函数体内读到 null 双下划线是编译器保留名，用户代码改用单下划线前缀
在原生程序里用了仅解释器函数 编译期报「该内置在原生后端缺席」 查 内置函数参考 的两列可用性
模块私有名与主程序撞名 编译期重定义失败 模块内私有名加模块前缀（如 _my_）
